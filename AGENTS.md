# Работа над Movie Recommendation API

Перед первой задачей прочитай `docs/PROJECT_CONTEXT.md`, затем проверь текущие файлы и `git status`. История ChatGPT служит контекстом, а актуальное состояние определяется кодом и проверками.

## Формат работы

- Общайся с пользователем по-русски. Имена в коде и существующие docstrings сохраняй в принятом английском стиле.
- Это учебный проект. Для существенного изменения кратко объясни проблему, решение и его причины; новые понятия объясняй на изменённом коде. Не усложняй архитектуру заранее.
- Codex в PyCharm реализует изменения и проверяет их. Отдельная задача Codex делает ревью PR. Пользователь принимает результат.
- Один спринт — одна feature-ветка и один PR. На каждую задачу Linear — отдельный коммит; не создавай отдельный PR для каждой задачи.
- Работай по текущему поручению: наличие всего roadmap не означает поручение реализовать его целиком. Двигайся небольшими понятными шагами внутри спринта.
- В коммитах и описании PR указывай соответствующие идентификаторы ANT-*. В PR перечисляй все закрываемые задачи и ссылки на них.
- Создавай коммиты, отправляй ветку и открывай PR, когда это входит в поручение пользователя. Merge и закрытие задач выполняй только по его поручению. Не отмечай задачу завершённой на основании одного отчёта агента.
- После работы сообщи изменённые файлы, результаты проверок, ограничения и следующий шаг. Для ревью подготовь описание поведения до/после и результаты тестов.

## Архитектура

- API → Service → Repository → PostgreSQL.
- Routers отвечают за HTTP и зависимости, Service — за бизнес-логику и границы транзакций, Repository — за доступ к данным без commit.
- Доменные исключения находятся в `app/core/exceptions.py`; преобразование в HTTP-ответы — в `app/api/exception_handlers.py`.
- Используй текущие async SQLAlchemy, Pydantic v2 и pydantic-settings. Не добавляй библиотеки без необходимости.
- Логи идут через стандартный logging в stdout. Используй `logging.getLogger(__name__)` и параметризованные сообщения. Избегай дублирования одной ошибки на нескольких уровнях.

## Окружение и проверки

- Выполняй команды из корня репозитория; используй `.venv/bin/python` (Python 3.13), чтобы не запускать случайный системный интерпретатор.
- Unit-тесты: `.venv/bin/python -m pytest -q`.
- Ruff: `.venv/bin/python -m ruff check .`.
- При ограничении записи кэшей: pytest с `-p no:cacheprovider`, Ruff с `--no-cache`.
- Запуск: `.venv/bin/python -m uvicorn app.main:app --reload`.
- Статус миграций: `.venv/bin/alembic current`. Применение миграций: `.venv/bin/alembic upgrade head` — меняет БД, выполняй в рамках задачи настройки/запуска.
- `.env` загружается относительно рабочей директории. Не выводи и не коммить секреты; шаблон настроек — `.env.example`.
- Для изменений поведения нужны содержательные проверки. Не ослабляй тесты только ради зелёного результата: сначала определи правильный контракт.
- Успешный `/health` не подтверждает работоспособность PostgreSQL. Проверяй `/health/db` и нужные сценарии отдельно.

## Сохранность работы

- Сохраняй существующие пользовательские изменения, особенно `.idea`. Не включай их в коммиты задачи.
- Не выполняй reset, очистку данных PostgreSQL или удаление Docker volumes без прямого разрешения.
- После подтверждённого этапа актуализируй `docs/PROJECT_CONTEXT.md`, если изменились состояние или план.
